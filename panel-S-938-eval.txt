### Findings

**Axiom checks (explicit, per instructions):**

- Prelude speaks the Rust protocol: PASS. `split_params`, `annotation_to_runtime_type`,
  `build_seq`, `value_matches_type`, `build_seq` are all general-purpose evaluation
  mechanisms. No Rust code special-cases prelude-specific names or functions.
  `Type::Unknown` fallback in `annotation_to_runtime_type` is a runtime enforcement gap
  for non-primitive TyCons (T-1691), not a prelude accommodation.

- No fast paths, no fallbacks, no backwards compatibility: PASS. The unannotated-rest
  fast path (`bucket_types.is_empty()`) in `bind_args_thunks` (eval_call.rs:406) is not
  a fast path in the prohibited sense — it is the correct behavior for the unannotated
  case. Materializing when there are no typed buckets would be premature materialization
  and would violate the laziness invariant. The two paths are semantically distinct, not
  one being a shortcut of the other.

- Correctness, not performance: PASS. Materialization in the typed-bucket path is
  necessary (analogous to TypeAssert). `build_seq` uses the correct right-to-left fold.
  `split_params` uses `position(|p| p.variadic)` to find the FIRST variadic as the
  boundary, which is the right anchor for invariant enforcement.

- Loader/prelude agnosticism: PASS. All new functions are general-purpose with no
  assumption about what is in the prelude. The exhaustiveness warning fires regardless
  of prelude content.

- General case, not specific: PASS. The dispatch is the general N-bucket + optional
  fallback pattern. No bucket count or type is hardcoded.

**Materialization audit:**

`materialize(&arg_thunk, Some(call_span), ctx).await?` at eval_call.rs:409 is
**Necessary**. The runtime type of the value must be inspected to route it to the
correct typed bucket. This is structurally identical to TypeAssert (which also forces
at the annotation site) and to `$if` (which forces the condition). No alternative design
avoids forcing here.

The original `tid` (ThunkId) is preserved and pushed into `typed_buckets[bucket_idx]`
at line 414 — NOT a freshly allocated thunk from the materialized value. The thunk is
now Materialized (memoized) in the thunk graph after the `materialize` call, so
subsequent accesses don't force it again. Thunk graph identity is correctly preserved.

The unannotated-rest path (lines 421-423, 447) passes `tid` directly without
materialization. This is correct: no type inspection is needed, so no forcing occurs.

Named args always go to rest (line 447) without materialization — correct: names carry
caller intent and type discrimination is not applied.

---

**`annotation_to_runtime_type` returning `Type::Unknown` for non-primitive TyCons:**

FINDING: `annotation_to_runtime_type` (eval_call.rs:534-553) returns `Type::Unknown`
for `@Bool`, `@MyType`, `@Expr`, and all other non-primitive Simple annotations. When
`value_matches_type` is called with `Type::Unknown` as the expected type,
`is_consistent_subtype` returns `true` for any value (eval.rs:982-983). This means a
typed bucket annotated with a non-primitive TyCon silently accepts ALL values —
functioning as a wildcard bucket. SCOPE: fix-later | FILE: eval_call.rs:534-553 |
Tracked: T-1691.

**Consequence of Type::Unknown bucket ordering:** If a non-primitive TyCon bucket
(which resolves to Unknown = accept-all) appears before a primitive bucket in declaration
order, the non-primitive bucket shadows all subsequent buckets — all args will match the
first Unknown bucket. Example: `[fn [let ...bools@Bool ...ns@Int] ...]` where `@Bool`
resolves to Unknown: every arg (including ints) routes to `bools`, leaving `ns` always
empty. This is a semantic correctness issue for mixed-type multi-variadic functions
involving non-primitive TyCons. The type checker at the call site cannot warn about this
because the type checker does see `Bool` as a concrete type (it doesn't know that the
runtime cannot discriminate it). SCOPE: fix-later | FILE: eval_call.rs:406-418 |
Tracked: T-1691 (the tracker description should note the bucket-shadowing consequence
explicitly). This is not a new issue introduced by this sprint — it is a documented
limitation of the current approach.

**`split_params` ordering-violation in release mode:**

The `debug_assert!` at eval_call.rs:511-516 fires only in debug mode. In release mode,
if a user function has `...rest ...ns@Int` ordering (typed variadic after untyped rest),
`split_params` silently places `ns` into `typed_variadics` after `rest` is already set,
producing inverted slot assignments relative to declaration order. This causes data
corruption at runtime (the wrong thunk reaches the wrong parameter name). The type
checker catches this ordering as an error (typecheck_cek.rs:2745-2753), surfaced as
`tc-warnings` in the test-loader. For well-typed programs the invariant holds.
For --no-typecheck paths or programs that ignore type-checker errors, the runtime
behavior would be incorrect. SCOPE: fix-later | FILE: eval_call.rs:511-516. Consider
converting the `debug_assert!` to a runtime `EvalError` for defense in release mode.
Not introduced by this sprint — design decision. Not a blocker given type-checker
enforcement.

**`build_seq` uses `call_env_id.0` (scope_env_id) for anonymous tail thunks:**

`build_seq` at eval_call.rs:569-589 allocates tail thunks via
`ctx.alloc_thunk(scope_env_id, tail_thunk)` where `scope_env_id` is the call frame's
`env_id.0`. Anonymous thunks (already-materialized Seq/Dict values) don't need a scope
association, but using the call frame scope is harmless — they are Materialized and will
never look up variables. No issue.

---

**`build_seq` returns an `Arc<Thunk>` wrapping `Value::Seq { head, tail }` where the
Seq's `head` ThunkId is the original arg ThunkId:**

This is correct. The head ThunkId points to the original arg thunk (now Materialized
after the type dispatch in the typed-bucket path). The consumer of the Seq (e.g., `head`
builtin) will call `get_thunk(head_tid)` and get the already-Materialized thunk — no
re-forcing needed. For the unannotated-rest path, args go to a Dict, not a Seq, so
`build_seq` is not involved.

---

**`build_seq` empty case returns `Value::Dict({})` (Seq nil sentinel):**

At eval_call.rs:576, the nil is `Thunk::value(Value::Dict(IndexMap::new()), span)`. This
is the universal Seq terminator, consistent with builtin_seq_prim.rs (head/tail error on
empty dict) and with the prior BIND-VARIADIC implementation (mempalace: 2026-05-13
migration). Correct.

---

**`build_seq` for empty typed bucket:**

When a typed bucket receives no args, `typed_buckets[bucket_idx]` is an empty Vec.
`build_seq(&[], ctx, call_span, call_env_id.0)` is called, which returns the nil
sentinel (empty dict). This means the parameter sees `Value::Dict({})` — the user can
test `[seq? ns]` → false (it's an empty dict, not a Seq), consistent with the Seq
protocol. Correct and consistent.

---

**Thunk lifecycle: no InProgress bypass:**

The materialization at eval_call.rs:409 goes through the full `materialize()` path,
which sets `InProgress` before evaluating, cycles fire correctly, and memoizes to
`Materialized` on success. No shortcut.

**Span propagation:**

The `materialize` call passes `Some(call_span)` as the `mat_span`, so errors from
arg evaluation during typed-bucket dispatch will have the call site as their
materialization span. Correct.

**Depth limiting:**

`materialize` at eval_call.rs:409 does not pass a `depth` argument directly — it uses
the caller's depth via the `ctx`. The CEK runner handles depth limits correctly.

### Verdict

APPROVE

All Round 8 findings are verified addressed. T-1689 (evaluator runtime type-discriminated
routing) is correctly implemented:

1. `split_params` correctly partitions fixed / typed_variadic / rest params.
2. `annotation_to_runtime_type` correctly handles primitive TyCons and falls back to
   Type::Unknown (accept-all) for non-primitives, consistent with gradual typing (AGT)
   semantics. T-1691 tracks full resolution.
3. Materialization in the typed-bucket path is necessary (strictness point for type
   dispatch, parallel to TypeAssert). The original ThunkId is reused — no redundant
   thunk allocation.
4. `build_seq` correctly constructs Seq cons-lists right-to-left. Empty bucket → nil
   sentinel (Value::Dict({})). Consistent with the Seq protocol.
5. Unannotated-rest path: zero materialization. Thunks pass through as-is. Laziness
   invariant preserved.
6. Named args route to rest, never to typed buckets. Correct.

All five axioms pass. No critical or major eval-engine findings. Two fix-later items
(T-1691 bucket shadowing consequence, and missing Type::Unknown shadowing corpus test)
are tracked and do not block approval.
