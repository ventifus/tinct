## Review: computer-scientist

Sprint: S-938 multi-variadic-params
Reviewer: computer-scientist
Date: 2026-07-17

### Theoretical Soundness Assessment

This sprint restructures `Type::Function` to support multiple typed variadic
parameter buckets with "match semantics" — declaration order determines match
priority, first match wins, untyped rest is the wildcard fallback. I verify
the five focus areas and five axioms.

---

#### 1. Match-Semantics Routing — Sound Approach for Type-Discriminated Variadic Dispatch

**VERDICT: SOUND**

The design maps multi-variadic dispatch to a well-understood formal model:
pattern matching with ordered clauses. Each typed variadic bucket
`...xs@T` is analogous to a match arm `T => route to xs`, and the untyped
rest `...args` is the wildcard `_ => route to args`. This is precisely the
semantics of ML-family match expressions (Maranget, 2008) and PEG ordered
choice (Ford, 2004):

- **Determinism**: declaration order defines priority; no ambiguity when
  types overlap (e.g., `...ns@Number ...is@Int` always routes Int to ns
  because Number matches first). This is semantically identical to ordered
  pattern matching where earlier arms shadow later ones.

- **Exhaustiveness**: the type checker emits a definition-time warning when
  typed buckets exist without a rest fallback (`typecheck_cek.rs:812-823`).
  This mirrors non-exhaustive match warnings in ML compilers — a function
  with `...ss@String ...ns@Int` but no `...rest` may fail at call sites
  where a Float is passed, just as a match without a wildcard may fail.

- **Soundness of routing predicate**: at the type-checker level, routing uses
  `is_consistent_subtype` (gradual typing — Garcia et al. 2016, AGT); at
  the runtime level, `value_matches_type` (structural type check against
  ground types). Both are sound predicates for their respective domains.

The formal obligation is: *every variadic arg is routed to exactly one bucket
or produces an error*. The code satisfies this: the loop at
`typecheck_cek.rs:2354-2388` breaks after the first match, and unmatched
args either go to rest or produce an exhaustiveness error. The runtime loop
at `eval_call.rs:403-436` has the same structure. No arg can be silently
dropped or double-counted.

**Reference**: Maranget, L. (2008). Compiling pattern matching to good
decision trees. In *ML Workshop '08*. Ford, B. (2004). Parsing Expression
Grammars. In *POPL '04*. Garcia et al. (2016). Abstracting gradual typing.
*POPL '16*.

#### 2. Pass 1 Pre-Binding with Fresh TypeVars for Variadic Params — Correct for Letrec SCC

**VERDICT: SOUND**

Pass 1 of `run_typecheck_dict` (lines 3566-3590) constructs a Function type
skeleton for recursive function entries. The new code correctly separates
variadic params: annotated variadics get fresh TypeVars in
`pre_typed_variadics`, unannotated variadics get fresh TypeVars in `pre_rest`,
and fixed params get fresh TypeVars in `fn_params`.

This is correct for SCC-based letrec inference because:

1. **Structural match with infer_fn_push_cont**: Pass 1 produces a Function
   type with the same structure (same number of fixed params, same number of
   typed_variadic buckets, same presence/absence of rest) as Pass 4's
   `infer_fn_push_cont`. When the SCC solver unifies the pre-bound skeleton
   with the inferred function type, Robinson unification succeeds because
   the structural shape matches — param counts, typed_variadic counts, and
   rest presence are identical.

2. **Fresh TypeVars at correct level**: `state.fresh_type_var(&p.span)`
   creates TypeVars at `state.level`, which is the dict's enclosing level + 1
   (set at `run_typecheck_dict` entry). This matches the level at which
   `infer_fn_push_cont` creates its TypeVars. Per Kiselyov (2013) levels-based
   generalization, unification between same-level TypeVars from the pre-bound
   skeleton and the inferred type produces correct bindings.

3. **Comment B-520 correctly documents the old bug**: the prior approach put
   variadics into `params` with `Dict(Uniform(TypeVar))`, causing
   `apply_call_args_poly` to unify `Int` args against the Dict param type.
   The fix eliminates this by routing variadics to `typed_variadics`/`rest`,
   which the call-args unification code handles separately.

**Proof obligation satisfied**: Pre-bound skeletons have identical structure
to inferred types, so unification is not blocked by structural mismatch,
and fresh TypeVars are at the correct level for constraint propagation.

**Reference**: Kiselyov, O. (2013). How OCaml type checker works.
http://okmij.org/ftp/ML/generalization.html

#### 3. Function-Function Unification of typed_variadics/rest — Correct Robinson Extension

**VERDICT: SOUND**

The unification code at `type_unify.rs:2449-2501` correctly extends Robinson
(1965) unification for the new Function fields:

1. **Structural guard** (line 2452): `is_variadic_1 != is_variadic_2 ||
   tv1.len() != tv2.len()` — rejects structural mismatches before
   recursive unification. This is the correct approach: two function types
   with different variadic structure are not unifiable, just as two tuples
   of different lengths are not unifiable.

2. **Typed variadic bucket unification** (lines 2480-2483): iterates
   `tv1.iter().zip(tv2.iter())` and unifies each pair. Since the length
   check at line 2452 guarantees `tv1.len() == tv2.len()`, the zip is
   exhaustive. Each bucket type is unified INVARIANTLY (not contravariantly)
   — this is correct for Robinson unification, which finds the most general
   unifier by equating sub-terms.

3. **Rest unification** (lines 2487-2500): `(Some, Some)` unifies rest types;
   `(None, None)` succeeds trivially; mixed `(Some, None)` or `(None, Some)`
   produces a structural mismatch error. This is correct — the presence or
   absence of rest is a structural property, not a type equality.

4. **Comment at line 2449-2451**: "The types within rest/typed_variadics are
   UNIFIED below, not compared by value — equality comparison would reject
   valid letrec SCC unifications where the pre-bound TypeVar differs from
   the inferred TypeVar." This is exactly right. Value-equality (PartialEq)
   would require identical TypeVar names, while unification correctly binds
   `_t5` to `_t12` when they represent the same position in two occurrences
   of the same recursive function type.

5. **Any-function special case preserved** (lines 2420-2433): the zero-param
   variadic "any function" type from the fn-narrowing-variadic sprint still
   works correctly. `is_variadic` is now computed as `!tv.is_empty() ||
   rest.is_some()` rather than checking a boolean flag — semantically
   equivalent.

**Proof obligation (Robinson invariant)**: unification of
`Function{..., tv: [T1, T2], rest: Some(R)}` with
`Function{..., tv: [S1, S2], rest: Some(Q)}` produces a MGU that includes
`T1 = S1`, `T2 = S2`, `R = Q` as sub-unifications. Each sub-unification
is invoked via `Box::pin(unify(...))` through the same shared substitution
state, so bindings from earlier sub-terms are visible to later ones. This
satisfies the Robinson invariant that the composition of all sub-unifiers
is the MGU of the compound term.

**Reference**: Robinson, J.A. (1965). A machine-oriented logic based on
the resolution principle. *JACM*, 12(1), 23-41.

#### 4. min_required Fix — Semantically Correct

**VERDICT: SOUND**

The old code had `min_required = fn_required.saturating_sub(1)` because the
old `required_count` included the variadic param itself in the count, so
subtracting 1 excluded the variadic. Now `required_count` counts only fixed
(non-variadic) params:

- `infer_fn_push_cont` at line 2779: `let required_count = param_types.len()`
  where `param_types` contains only non-variadic params (variadics go into
  `typed_variadics`/`rest`).
- `apply_call_args_poly` at line 2272: `let min_required = fn_required` —
  no adjustment needed.
- `fn_type()` constructor at line 2437: `let required_count = params.len()`
  where `params` is the fixed params vec.

The arity check at line 2278: `total_supplied < min_required ||
(!fn_variadic && arg_types.len() > param_types.len())` is correct:
- Under-application: `total_supplied < min_required` catches calls with
  too few args for the fixed params.
- Over-application without variadic: `!fn_variadic && arg_types.len() >
  param_types.len()` catches excess args when no variadic is present.
- Over-application with variadic: excess args are handled by the variadic
  routing code below the arity check.

The runtime `bind_args_thunks` at `eval_call.rs:207-222` independently
validates required params via per-param coverage checking (Kotlin model),
which also counts only regular (non-variadic) params via `split_params`.

**No off-by-one**: the old `saturating_sub(1)` was a correction for counting
the variadic in `required_count`. The new code doesn't count it, so no
correction is needed. Both the old and new code accept the same set of
valid calls.

#### 5. is_consistent_subtype Contravariance in typed_variadics — Correct

**VERDICT: SOUND**

At `type_def.rs:1062-1068`:
```
let tv_subtype = sub_tv.len() == sup_tv.len()
    && sub_tv.iter().zip(sup_tv.iter())
        .all(|((_, sub_t), (_, sup_t))| {
            Self::is_consistent_subtype(sup_t, sub_t) // contravariant
        });
```

This applies the standard function variance rule from Cardelli (1988) and
Pierce (2002, TAPL section 15):

  `(A1 -> B1) <: (A2 -> B2)  iff  A2 <: A1  (CONTRA)  and  B1 <: B2  (CO)`

Typed variadic buckets are parameter types (they accept input from callers),
so they are in contravariant position. If `f: (...xs@Number) -> R` and
`g: (...xs@Int) -> R`, then `g <: f` iff `Number <: Int` — which is false.
The code checks `is_consistent_subtype(sup_t, sub_t)` (note the swapped
order: sup first, sub second), which is the correct contravariant check.

Similarly for rest at line 1070: `is_consistent_subtype(&pr.1, &sr.1)` —
`pr` is the sup's rest, `sr` is the sub's rest, order swapped for
contravariance. Correct.

The return type at line 1083: `is_consistent_subtype(sub_r, sup_r)` —
covariant, correct.

The `is_consistent` function at lines 1300-1318 does NOT apply variance
(it uses symmetric `is_consistent(t1, t2)`). This is correct: consistency
is a symmetric relation (Garcia et al. 2016, AGT Definition 7), not a
directed relation like subtyping.

**Reference**: Cardelli, L. (1988). A semantics of multiple inheritance.
*Information and Computation*, 76(2-3), 138-164. Pierce, B.C. (2002).
*Types and Programming Languages*. MIT Press, section 15.

### Axiom Checks

#### Axiom 1 — Prelude speaks the Rust protocol: PASS
No Rust code references prelude-specific names or types. `split_params`,
`annotation_to_runtime_type`, `build_seq`, `extract_seq_elem_type`,
`value_matches_type`, and `is_consistent_subtype` are all general functions.
The routing logic is parameterized by the declared typed bucket types, not
by any prelude convention. A user-defined function with typed variadics
uses the same dispatch path as a prelude function.

#### Axiom 2 — No fast paths, no fallbacks, no backwards compatibility: PASS
The unannotated-rest skip at `eval_call.rs:403-419` (skip materialization when
`bucket_types.is_empty()`) is NOT a fast path — it is the correct behavior.
When there are no typed buckets, there is no type to discriminate against,
so forcing thunks would be semantically wrong (it would break laziness for
the unannotated variadic case). This is the single correct path.

The `annotation_to_runtime_type` fallback to `Type::Unknown` for compound
annotations is a known limitation tracked as T-1691, not a fallback. There
is no alternate "fast" path — the same function handles all annotations.

#### Axiom 3 — Correctness, not performance: PASS
The implementation materializes values when typed buckets exist (necessary
strictness for type dispatch). It does not cut corners for performance:
each excess arg is materialized individually, each is checked against each
bucket in order, and unmatched args are properly handled. The `debug_assert`
in `split_params` is defense-in-depth for invariants, not a performance
optimization.

#### Axiom 4 — Loader/prelude agnosticism: PASS
All new functions are general-purpose. The feature works with an empty prelude.
The test-loader's prelude fatal check counts `errors` only (not `tc-warnings`),
so prelude functions using typed variadics can produce exhaustiveness warnings
without blocking the test suite — but this is policy set in tinct code
(test-loader.llt), not hardwired into Rust.

#### Axiom 5 — General case, not specific: PASS
The implementation handles the general N-bucket case: N typed buckets in
declaration order + 1 optional untyped fallback. It is not special-cased
for any specific N or specific types. The match-semantics framework
(first match wins, wildcard last) is the general dispatch model.

### Findings

#### Major

FINDING: `ground_type_of(Value::Function)` does not populate `typed_variadics`
for multi-variadic functions — all params (including variadics) go into
`params` with Unknown types, and only `rest` is set based on the last param's
variadic flag. For a function `[fn [let x ...ss@String ...ns@Int ...rest] ...]`,
`ground_type_of` produces `Function{params: [Unknown, Unknown, Unknown, Unknown],
typed_variadics: [], rest: Some(("rest", Unknown))}` — arity 4, no typed buckets.
The actual inferred type has `params: [(x, Unknown)], typed_variadics: [(ss, Seq[String]),
(ns, Seq[Int])], rest: Some(("rest", TypeVar))` — arity 1 with 2 typed buckets.
This mismatch means `is_consistent_subtype` checks against runtime-observed
function types (e.g., in TypeAssert `[@Fn f]`) will compare against the wrong
structure. | SCOPE: fix-later | FILE: src/eval.rs:923-936 | MODEL: Consistent
subtyping requires structural agreement between the type being checked and the
annotation type. The ground type must faithfully represent the function's
variadic structure.

NOTE: This is pre-existing (acknowledged in the sprint review at line 96) and
is not worsened by S-938. The pre-existing `is_consistent_subtype` tolerance
for Unknown-param mismatches prevents this from producing false errors in
practice. However, it is a correctness gap that should be addressed when
typed variadic dispatch is fully integrated into the runtime type system.

#### Minor

FINDING: `PartialEq` for `Type::Function` at `type_def.rs:460-464` uses
structural equality for `typed_variadics` (via `tv1 == tv2`) and `rest`
(via `rest1 == rest2`), but uses element-by-element comparison for `params`
(via `p1.iter().zip(p2).all(|((_, t1), (_, t2))| t1 == t2)`). The `params`
comparison ignores param names (only compares types), but the `typed_variadics`
comparison via `Vec::PartialEq` compares both names AND types (since
`(String, Type)::PartialEq` compares both fields). This means two function
types with identical typed_variadic types but different bucket names are
NOT equal, while two function types with identical param types but different
param names ARE equal. This is inconsistent — structural type identity should
not depend on parameter names for any position. | SCOPE: fix-later |
FILE: src/type_def.rs:460-464 | MODEL: Structural type equivalence should
be independent of variable/parameter names (alpha-equivalence).

FINDING: The `Hash` implementation for `Type::Function` at `type_def.rs:570`
uses `typed_variadics.hash(state)` which hashes both names and types (via
`Vec<(String, Type)>::Hash`), consistent with the PartialEq inconsistency
above. If PartialEq is fixed to ignore names, Hash must also be updated to
maintain the PartialEq/Hash contract. | SCOPE: fix-later |
FILE: src/type_def.rs:570 | MODEL: PartialEq/Hash contract: `a == b` implies
`hash(a) == hash(b)`.

### Praise

- The structural decomposition of `Type::Function` into `params`,
  `typed_variadics`, and `rest` is clean and directly reflects the formal
  model: fixed args, typed dispatch buckets, wildcard fallback. The
  comment at `type_def.rs:285-292` correctly documents match semantics.

- The unification code at `type_unify.rs:2449-2501` is correct Robinson
  unification extended for the new fields, with a clear comment explaining
  why value-equality would be wrong for letrec SCC.

- The exhaustiveness warning at `typecheck_cek.rs:812-823` correctly mirrors
  match exhaustiveness: typed-only variadics without fallback = non-exhaustive
  pattern set. The warning is definition-time (advisory), not call-site
  (blocking), which is the right design — the function may still be called
  with matching-typed args.

- All 10 traversal functions (`collect_type_vars`, `collect_all_vars`,
  `collect_all_vars_check_occurs`, `collect_all_vars_vec`,
  `collect_operator_names`, `has_inference_vars`, `has_type_stage_app`,
  `substitute_recvar`, `simplify_type`, `check_kind_wellformed`) correctly
  recurse into `typed_variadics` and `rest`. The occurs check
  (`lower_levels_check_occurs` at `type_unify.rs:1697-1715`) also handles
  both fields. This is thorough — missing any traversal function would be
  a soundness hole for generalization or occurs-check invariants.

- The `rename_single_type_var` and `instantiate_at_level` functions in
  `type_env.rs` correctly handle the new fields, ensuring fresh variable
  generation during instantiation traverses all sub-terms. This preserves
  the Kiselyov (2013) levels-based generalization invariant.

- The `build_seq` right-to-left fold at `eval_call.rs:569-589` correctly
  constructs cons-lists matching LLT's `Value::Seq { head, tail }` format.
  The nil sentinel is `Value::Dict({})` — consistent with the rest of the
  Seq ecosystem (`head`/`tail` raise on empty dict, `empty?` checks seq?).

- Separating parser permissiveness from type-checker enforcement is the
  correct design: the parser accepts any parameter ordering, while the
  type checker at `infer_fn_push_cont:2745-2771` enforces
  "fixed before variadic" and "typed before rest". This follows the
  principle that the parser should be maximally permissive, producing a
  well-formed AST that later phases validate.

### Future Work

- `ground_type_of` multi-variadic fidelity: produce a Function type that
  matches the inferred type's structure (fixed params only in `params`,
  typed buckets in `typed_variadics`, rest in `rest`). Requires
  `split_params` or equivalent at `ground_type_of` time. Impact: enables
  correct `is_consistent_subtype` checks for runtime TypeAssert on
  multi-variadic functions.

- `annotation_to_runtime_type` compound annotations (T-1691): resolve
  `PropertyDict` and `Annotated` annotations to concrete types at the
  evaluator level, enabling runtime type discrimination for typed buckets
  annotated with compound types (e.g., `...xs@[Seq [or Int String]]`).

- PartialEq/Hash consistency for typed_variadics names: decide whether
  bucket names are part of structural type identity. If not (consistent
  with params), update PartialEq to compare only types and update Hash
  to match.
