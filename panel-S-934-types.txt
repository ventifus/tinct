## Review: type-theorist

### Findings

- FINDING: `try_eq_literal` hardcodes `"true"` and `"false"` identifier names and emits `Type::Unknown` as the narrowed type (src/typecheck_narrow.rs:157-161). This is a double violation: (1) hardcoding prelude-defined boolean identifier names violates Axiom 4 (loader/prelude agnosticism), and (2) producing `Unknown` as the narrowed type is unjustified — it actively degrades type inference in the true branch of `[= x true]` / `[= x false]` conditions. When `x` is narrowed to `Unknown`, the true branch loses all static type information for `x`. The correct behavior when `true`/`false` can't be typed is to return `None` from `try_eq_literal` (no narrowing, `x` retains its original type) rather than `Type::Unknown` (which replaces `x`'s type with the gradual wildcard). The comment incorrectly associates this with B-545 (`"Bool"/"Seq" in try_type_of`), which is a distinct issue. This `Unknown` emission is unjustified and is a fix-now violation per Unknown policy. | SCOPE: fix-now | FILE: src/typecheck_narrow.rs:154-162

- FINDING: Deletion of the `fn?` hardcoded arm in `extract_narrowings` (Round 2 fix, C-512 Finding 1) introduces a behavioral regression: `fn?` no longer narrows its argument to the "any function" type in the true branch. The annotation-based fallthrough path (`_ if args.len() == 1`) requires `fn?`'s scheme to have `param_narrowings[0] = Some(T)`, which requires `fn?`'s first parameter to carry `@[is: FunctionType]` — but `Function` is not an expressible type name in the tinct annotation language. There is no `TypeNode.Function` or `Type::TyCon("Function")` path that `@[is: ...]` can resolve to. The sprint review (C-511) stated "annotation-based arm covers them" but this is only true for `int?`, `str?`, `dict?`, `float?`, `null?`, `num?` (which have `@[is: T]` annotations in prelude.llt lines 1928-1933,1937). For `fn?` (line 1934, no `@[is: T]`) and `seq?` (line 1936, no `@[is: T]`), no annotation-based replacement exists. The prior behavior (narrowing to the any-function type) is not recoverable via the current annotation mechanism. This is a type correctness regression. | SCOPE: fix-now | FILE: src/typecheck_narrow.rs:116-128 and stdlib/prelude.llt:1934,1936

- FINDING: Both Source 1 (`@[narrows: T]`) and Source 2 (`@[is: T]`) in Pass 4 (typecheck_cek.rs:4566-4627) only handle bare `VarRef` type names. If the annotation value is a compound type expression like `@[narrows: [Seq Int]]` or `@[is: [or Int Str]]`, the `if let SurfaceExpression::VarRef { name: type_name, .. }` match fails silently and the narrowing is not registered. The code falls through to `Vec::new()` with no diagnostic. This means compound narrowing types are silently ignored. Since `resolve_annotation` already handles compound type expressions (PropertyDict, Annotated, etc.), the fix is to use `eval_type_stage_expr` or build a proper `Annotation` from the node rather than requiring a bare `VarRef`. | SCOPE: fix-later | FILE: src/typecheck_cek.rs:4566-4590 (Source 1), 4598-4624 (Source 2)

- FINDING: `extract_binding_types` (src/typecheck_narrow.rs:347-351) emits `Type::Unknown` for `SurfaceExpression::Call` patterns like `[Int]` or `[Result String]`. The comment says "Full parametric type resolution from annotation expressions is future work." Using `Unknown` here is the gradual escape hatch, but for a pattern position where a type application is written by the user, `Unknown` silently disables type checking. A fresh `TypeVar` would be more principled (matches any type without disabling checking), mirroring the bare-identifier path at line 383-385 which correctly uses `state.fresh_type_var`. The `Placeholder` arm at line 387-389 (`_` wildcard) producing `Unknown` is justified (explicit opt-out). The `Call` arm is not. | SCOPE: fix-later | FILE: src/typecheck_narrow.rs:347-351

- FINDING: `try_type_of` (src/typecheck_narrow.rs:191-201) hardcodes `"Int"`, `"Float"`, `"String"` as type name strings that map to primitive types, and `"Bool"` / `"Seq"` to `Type::Unknown`. The primitive arm hardcodes Rust type constructors to string literals from a type-of runtime check — this is an Axiom 4 violation (the strings `"Int"`, `"Float"`, `"String"` are runtime representations of prelude-defined type names). The `"Bool"` / `"Seq"` → `Unknown` is unjustified: returning `None` would be more correct (no narrowing, variable retains its type) vs. inserting `Unknown` (variable loses its type). This is tracked as B-545 for the hardcoding; the `Unknown` emission is a distinct fix-now Unknown policy violation. | SCOPE: fix-now (Unknown emission) / fix-later (hardcoding, tracked B-545) | FILE: src/typecheck_narrow.rs:191-201

- FINDING: Module-level doc comment in typecheck_narrow.rs line 25 states "Predicate narrowing (`@[is: T]`, `@[narrows: T]`) is entirely annotation-driven — no predicate names are hardcoded in Rust." This is inaccurate for `fn?` and `seq?`: those predicates lack `@[is: T]` annotations in prelude.llt (lines 1934, 1936), so they receive no narrowing via the annotation path. The claim of "entirely annotation-driven" is only true after prelude adds `@[is: T]` to every predicate that previously had a hardcoded arm. Until then, the doc is aspirational, not factual. | SCOPE: fix-now | FILE: src/typecheck_narrow.rs:25 and doc/feature/narrowing.md

- FINDING: `TypeScheme.param_narrowings` is `Vec<Option<Type>>` with index-parallel semantics (index 0 = first parameter, index 1 = second parameter, etc.), but `extract_narrowings` only ever reads `param_narrowings.first()` (index 0) regardless of which argument position the call targets. This is fine for current use (all narrowing predicates target their first argument), but the data model promises per-parameter narrowing that is never used. If the data model is always first-parameter-only in practice, the type should be `Option<Type>` (a single optional type), not `Vec<Option<Type>>`. The Vec implies multi-parameter narrowing is supported, but no consumer reads beyond index 0 and no producer currently fills beyond index 0. | SCOPE: fix-later | FILE: src/type_infer.rs:199, src/typecheck_narrow.rs:120-121

- FINDING: `TypeScheme::mono` initializes `param_narrowings: Vec::new()`, which is correct. However, the `TypeScheme` struct-literal construction at typecheck_cek.rs:4183-4192 (class method scheme registration) also initializes `param_narrowings: Vec::new()`. This is consistent. No issue here — confirming correctness of all TypeScheme construction sites. | SCOPE: fix-now (praise / N/A) | FILE: N/A

- FINDING: Pass 4 annotation extraction in typecheck_cek.rs: Source 2 only fires when `entry.node.value.expr` is directly `SurfaceExpression::Fn`. If the predicate function is defined via a more complex expression (e.g. a VarRef alias, or a call to a higher-order combinator), the match fails and Source 2 contributes nothing. This is acceptable for the common case (direct fn definitions), but the limitation should be documented. Currently there is no comment explaining that Source 2 only examines direct fn literals. | SCOPE: fix-later | FILE: src/typecheck_cek.rs:4594

- FINDING: `patterns_can_unify` (src/typecheck_narrow.rs:484-486) uses structural equality (`ty_a == ty_b`) as a "conservative approximation" for unification. This is a pre-existing design choice, not a sprint regression, but it means two structurally equivalent types that differ only in their TypeVar names will not be detected as unifiable, causing false "non-overlapping" results. The comment correctly documents this limitation. Confirmed pre-existing — no S-934 regression. | SCOPE: fix-later | FILE: src/typecheck_narrow.rs:484-486

- FINDING: The `as-typenode` protocol name (typecheck_annot.rs:4921) is still a bare string literal `"as-typenode"`. The D-6 decision is referenced in the doc comment but no D-6 tracker item was created (C-510 Fix Review states "D-6 tracker decision for as-typenode... should be created"). This is a tracking gap rather than a code issue, but the tracker item must exist per the CLAUDE.md rule "anything deferred must exist as a tracker item." | SCOPE: fix-now | FILE: doc comment references D-6 but no D-6 item exists in tracker

### Verdict

REQUEST_CHANGES

Fix-now findings:

1. `try_eq_literal` true/false → `Unknown`: change to return `None` instead (src/typecheck_narrow.rs:157-161).

2. `try_type_of` "Bool"/"Seq" → `Unknown`: change to return `None` instead of producing `Unknown` narrowing types (src/typecheck_narrow.rs:198-199).

3. `fn?` regression: the deletion of the `fn?` hardcoded arm broke true-branch narrowing with no annotation-based replacement. Either (a) restore the `fn?` arm with a documented Axiom 1 protocol declaration, or (b) add `@[is: ...]` annotation support for the function type to prelude.llt `fn?`. Until resolved, `fn?` narrowing is silently broken.

4. Doc comment "entirely annotation-driven — no predicate names are hardcoded" is false until prelude adds `@[is: T]` to `fn?` and `seq?`. Fix the comment to say "predicate narrowing is annotation-driven for predicates that carry `@[is: T]` or `@[narrows: T]` annotations" and note that `fn?` and `seq?` do not yet declare narrowing via annotation.

5. Create D-6 tracker decision item for `as-typenode` as Axiom 1 protocol entry (referenced in doc comments but not tracked).
