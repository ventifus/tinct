### Axiom Checks (explicit per-axiom verification)

**Prelude speaks the Rust protocol — PASS**
`value_matches_type`, `is_consistent_subtype`, `annotation_to_runtime_type`, `split_params`, and
`build_seq` are all general-purpose Rust functions. None of them inspect prelude names or
special-case any prelude-defined type. The exhaustiveness warning is emitted by the type checker
regardless of prelude content. The test-loader's fatal-check boundary (counting `errors` only, not
`tc-warnings`) is policy set in tinct code, not hardwired into Rust. The feature works correctly
with an empty prelude.

**No fast paths, no fallbacks, no backwards compatibility — PASS**
The unannotated-rest-only optimization in `bind_args_thunks` (eval_call.rs:403-419: skip
materialization when `bucket_types.is_empty()`) is not a fast path. It is the correct behavior
for the unannotated-rest case where type discrimination is unnecessary. Materializing thunks when
there are no typed buckets would force evaluation unnecessarily and violate the laziness guarantee.
One correct path; no legacy shim.

**Correctness, not performance — PASS**
The implementation materializes values at the typed-bucket routing boundary — a necessary
strictness point identical to TypeAssert. `build_seq` constructs cons-cells right-to-left,
which is the correct structural form for Value::Seq. The `debug_assert!(p.variadic, ...)` in
`split_params` provides defense-in-depth in debug builds. No correctness compromises for
performance were introduced.

**Loader/prelude agnosticism — PASS**
Multi-variadic typed buckets are a language feature, not a prelude feature. No part of the
implementation assumes any particular prelude is loaded. The `annotation_to_runtime_type` fallback
to `Type::Unknown` for compound annotations allows the feature to function in --no-typecheck or
empty-prelude contexts (at the cost of compile-time routing precision, tracked in T-1691).

**General case, not specific — PASS**
The bucket routing implements the general N-typed-buckets + 1-optional-untyped-fallback dispatch.
Match priority is declaration order for all N. `extract_seq_elem_type` handles the general
`App(TyCon("Seq"), T)` form and falls back to the type itself — not special-cased for specific
element types. `split_params` handles any number of typed variadic params and any annotation
type, not just the test cases.

### Cross-Layer Consistency

**Parser → Evaluator**

Parser (parser.rs:5608-5611) no longer enforces single-variadic or must-be-last constraints.
The `Param` struct's `variadic: bool` and `annotation: Option<Spanned<Annotation>>` fields
are set correctly by the parser and consumed by `split_params` in eval_call.rs:494-523.
`split_params` partitions on `p.variadic` (not annotation presence), matching the parser's
intent: all `...` params are variadic regardless of annotation.

**Slot assignment consistency (critical path verified)**

The resolver (resolve.rs:186-187) assigns slots by iterating `params` in declaration order via
`enter_scope(&param_names)`. `Scope::enter_scope` (arena.rs:57-63) assigns slot `i` to
`params[i]` via enumerate. The evaluator (eval_call.rs:285-298) allocates exactly `params.len()`
slots via `alloc_child` and fills them with `reserve_slot` in declaration order. The computed
slot assignments:
  - Fixed params: slot `i` (loop variable at line 307, used as `i as u32` at line 312)
  - Typed variadic bucket k: slot `regular_params.len() + k` (line 460)
  - Untyped rest: slot `regular_params.len() + typed_variadic_params.len()` (line 472)

For params `[x, ...ss@String, ...ns@Int, ...rest]` (declaration order):
  - x → slot 0 (resolver: position 0, evaluator: i=0)
  - ss → slot 1 (resolver: position 1, evaluator: 1+0=1)
  - ns → slot 2 (resolver: position 2, evaluator: 1+1=2)
  - rest → slot 3 (resolver: position 3, evaluator: 1+2=3)

These are identical. The cross-layer slot contract is satisfied.

**Type checker → Evaluator bucket type consistency**

For `...xs@String`:
  - Type checker: `resolve_annotation(Annotation::Simple("String"))` → `Type::Str`
  - Evaluator: `annotation_to_runtime_type(Annotation::Simple("String"))` → `Type::Str`

For `...ns@Int`:
  - Type checker: `Type::Int`
  - Evaluator: `Type::Int`

For `...xs@[Seq Int]` (Annotated form):
  - Type checker: `App(TyCon("Seq"), Int)` via `resolve_type_head`
  - Evaluator: `annotation_to_runtime_type(Annotation::Annotated(...))` → `Type::Unknown`

This last case is the T-1691 gap: the runtime cannot resolve compound annotations without the
full tycon_env. The type checker correctly enforces element-type routing at compile time; at
runtime the bucket accepts all values (Type::Unknown = accept-all). Not a soundness issue —
the type checker catches misrouted calls before they reach the evaluator in typed programs.
Correctly tracked in T-1691.

`extract_seq_elem_type` handles both paths correctly: `App(TyCon("Seq"), T)` → `T` (unwraps),
and `Type::Str` → `Type::Str` (fallback). The `is_consistent_subtype` routing check and the
unification target are therefore consistent with what `annotation_to_runtime_type` produces for
the same annotation.

**Pass 1 pre-binding in run_typecheck_dict (B-520 fix)**

The pre-binding at typecheck_cek.rs:3566-3590 correctly mirrors `infer_fn_push_cont`'s
`typed_variadics`/`rest` separation. Variadic params with annotations go to
`pre_typed_variadics`; unannotated go to `pre_rest`. This matches the runtime's `split_params`

**Ordering constraint enforcement**

Type checker enforces two ordering violations in `infer_fn_push_cont`:
1. Typed variadic after untyped rest (typecheck_cek.rs:2745-2754): error message is specific and
   actionable — names the violating param and explains the constraint.
2. Fixed param after any variadic (typecheck_cek.rs:2762-2770): error message names the fixed
   param and explains the constraint.

The evaluator's `split_params` has matching `debug_assert!` for both violations in debug builds.
In release builds, incorrect ordering is caught by the type checker before reaching eval in
well-typed programs.

**Exhaustiveness warning**

`AfterFnBody` (typecheck_cek.rs:812-823): warning fires when `!typed_variadics.is_empty() &&
rest.is_none()`. Uses `Type::normalize_union` to display covered types. `normalize_union` does
not panic on a non-empty Vec (panics only on empty). For a single-entry typed_variadics, it
returns the bare type (no `|` union). Correct.

The warning spans `node_span` (the Fn node span) — definition-site span. This is correct for a
definition-time advisory: it points to the function definition where the exhaustiveness gap exists.

**Span threading in apply_call_args_poly**

`span` at line 2261 is the call-site span from the `AfterCallFunc` continuation, where it was
set to `node.span.clone()` (typecheck_cek.rs:549) on the call node. All errors inside
`apply_call_args_poly` use `span.clone()`. Named arg errors use `na.span.clone()` (the named
argument node span). Both are real source spans. No `Span::default()` or `Span::origin()` in any
new error path.
