#### FINDING 1 — CRITICAL: UnevaluatedState::AnnotatedWrap materialization path has no corpus test

SCOPE: fix-now
FILE: src/eval_materialize.rs:1366–1386, src/eval_dict.rs:337–355, src/value.rs:1323

T-1621 introduced UnevaluatedState::AnnotatedWrap, which is created when a dict-key
has a PropertyDict annotation and the value is a non-literal thunk (function, VarRef, or
call expression). When materialized, it forces `inner` and produces Value::Annotated.

The existing dict_key_annotation.llt-eval test:
  [Pi@[doc: "mathematical constant"  precision: 5]: 3.14159]
  === out
  Dict({"Pi": Float(3.14159)})

Pi is a literal (Float). This hits the `try_get_materialized()` → Some branch in
eval_dict.rs line 337 — the AnnotatedWrap path is NOT exercised. The test passes even if
the AnnotatedWrap arm in dispatch_state is completely removed.

The AnnotatedWrap path fires only when the annotated value is non-literal — e.g., a
function, a VarRef reference, or a call. No corpus test verifies that:
  (a) A function-valued entry annotated with @[doc: "..."] produces Value::Annotated
  (b) The AnnotatedWrap thunk actually materializes to Value::Annotated when forced
  (c) annotation-of on such a value reads the annotation dict correctly

Mutation target: deleting the UnevaluatedState::AnnotatedWrap arm from dispatch_state
would silently error (unreachable or wrong value type) — but no corpus test would catch
the regression before the deletion.

Required test (eval/annotation-system/annotated_fn_property_dict.llt-eval):
  # Value::Annotated wrapping for non-literal (function) annotated dict entry (T-1621)
  [
    f@[doc: "adds one"]: [fn [let x] [+ x 1]]
    ann: [annotation-of f]
  ]
  === out
  Dict({"f": Function(x), "ann": Dict({"doc": String("adds one")})})

This would fail if AnnotatedWrap is not created or not materialized correctly.

#### FINDING 2 — CRITICAL: Annotation::Annotated round-trip (T-1618 inner-ann key) has no corpus test

SCOPE: fix-now
FILE: src/surface_fields.rs:644–659, src/surface_convert.rs:778–787

T-1618 changed Annotation::Annotated from (String, Box<Annotation>) to
(Box<Annotation>, Box<Annotation>), allowing PropertyDict as the outer annotation.
surface_fields.rs serializes Annotated by emitting both "inner" (flat string, backward
compat) AND "inner-ann" (structured recursive Annotation value) at lines 657–658.
surface_convert.rs deserializes by checking "inner-ann" first (line 778), falling back
to "inner" (line 784).

The "inner-ann" key is the entire purpose of T-1618's round-trip fix: if a non-Simple
inner annotation (e.g., PropertyDict or Annotated) is serialized, the flat "inner" string
loses structural information; "inner-ann" preserves it.

The existing chained_annotation.llt-eval test:
  [x@Integer@Integer: 42  x]
  === out
  Int(42)

This only verifies eval output, not the Annotation round-trip through
surface_fields/surface_convert. It does NOT verify that:
  - The "inner-ann" field is present in the serialized Annotation::Annotated payload
  - Deserializing "inner-ann" reconstructs the correct inner Annotation (PropertyDict case)
  - A PropertyDict outer + PropertyDict inner chain round-trips correctly
  - Mutation: removing the "inner-ann" field from surface_fields.rs line 657 would make
    all non-Simple inner annotations silently degrade to Simple on round-trip, but the
    existing test would still pass because "inner" (flat string) still exists and the
    inner annotation happens to be Simple("Integer").

Required test (eval/annotation-system/annotated_inner_ann_roundtrip.llt-eval):
  # T-1618: @[...]@[...] chained annotation round-trip — inner-ann field preserves
  # PropertyDict inner annotation through surface_fields serialization and
  # surface_convert deserialization.
  [
    # Annotated(PropertyDict([doc: "x"]), PropertyDict([type: Int])) form
    # Access annotation-of to force the round-trip through surface_fields/surface_convert
    f@[doc: "outer"]@[type: Integer]: [fn [let x] x]
    ann: [annotation-of f]
  ]
  === out
  ...

Note: if annotation-of cannot directly expose the chained annotation structure, the test
should at minimum use builtin-annotation-of or builtin-surface-fields to verify the
"inner-ann" key is present in the Annotated payload.

#### FINDING 4 — MAJOR: annotation_based_narrowing.llt-eval is overly loose — does not verify narrowing actually occurred

SCOPE: fix-now
FILE: tests/corpus/eval/typecheck/annotation_based_narrowing.llt-eval

The test verifies that [describe 41] → 42 and [describe "hello"] → "not an int".
This confirms the program evaluates correctly, but it does NOT verify that type narrowing
is active. If `extract_narrowings` never fires (param_narrowings never populated), the
test could still pass because [builtin-int-add x 1] at runtime accepts any value that is
actually an Int — the type checker's narrowing does not affect evaluation correctness.

The test also does not capture any type warnings (no === warn section). This is correct
IF the code is well-typed. But the test is not checking what it claims: that x is narrowed
to Int in the true branch. A mutation where param_narrowings is always Vec::new() would
not cause this test to fail.

The correct mechanism for verifying narrowing is a typecheck/warnings test: the narrowed
branch should produce zero warnings, while a test WITHOUT the @[is: T] annotation on the
same code pattern should produce a type warning (e.g., passing a non-Int to
builtin-int-add without narrowing).

However, since eval-mode tests run the full pipeline (including typecheck), the real
mutation risk is: typecheck narrowing is not occurring but the eval is correct because
the runtime type happens to be Int. A tighter test would use a typecheck warning to
confirm narrowing DID change the type environment (e.g., call a function that requires
exactly Int and verify no warning).

The key_annotation_narrows.llt-eval has the same looseness issue.

Both tests are acceptable as smoke tests that the feature doesn't crash, but neither is
tight enough to catch a subtly broken param_narrowings population path. They should be
supplemented by a test in tests/corpus/eval/typecheck/warnings/ that asserts:
  - WITHOUT @[is: T], passing x to builtin-int-add in the narrowed branch produces
    a type warning
  - WITH @[is: T], the same pattern produces no warning

This confirms the narrowing mechanism is actually being applied, not just that the
program happens to evaluate correctly.

### Axiom Check

- **Prelude speaks the Rust protocol**: PASS
  - annotation-based narrowing: param_narrowings is populated by Rust (typecheck_cek.rs),
    read by Rust (typecheck_narrow.rs). Prelude participates via @[narrows:]/[is:] annotations.
  - as-typenode: Rust defines the protocol (D-6 decision); prelude implements it.
  - AnnotatedWrap: Rust-defined thunk type; prelude has no awareness of it.
  - set_floating_annotation: pure parser Rust behavior.

- **No fast paths, no fallbacks, no backwards compatibility**: CONDITIONAL PASS
  - T-1618: "inner-ann" field adds forward path while "inner" field is kept for backward
    compatibility with "serialized data that predates the round-trip fix" (surface_convert.rs:776).
    The comment explicitly says "backward compatibility" — this is an Axiom 2 concern.
    The "inner" fallback path is justified only if there is no existing serialized data that
    will be read by production code; if the "Annotated" serialization format is only ever
    round-tripped within a single process invocation, the backward compat fallback is
    unnecessary complexity. Flag for review: if the "inner" fallback is truly needed, it
    must be documented as a temporary migration path with a tracker item to remove it.
    MINOR VIOLATION — not a fix-now finding, but should be tracked.

- **Correctness, not performance**: PASS
  - AnnotatedWrap uses deferred thunk (correct, lazy) rather than eager force (would break
    laziness guarantee for function-valued annotated entries).
  - type_stage_map uses HashMap O(1) lookup replacing iterative search — this is documented
    as a refactor, not a performance optimization introduced at correctness cost.

- **Loader/prelude agnosticism**: PASS
  - param_narrowings mechanism requires no hardcoded prelude predicate names.
  - as_type_dispatch requires "as-typenode" to exist in the prelude — this is a named
    protocol entry (D-6), not a hardcoded prelude dependency.
  - typecheck_narrow.rs module doc: "=", "and", "has?", "type-of" structural narrowing
    still hardcoded (B-545, tracked).

- **General case, not specific**: PASS
  - annotation-based narrowing works for any function, not just prelude predicates.
  - AnnotatedWrap applies to any non-literal annotated entry, not just functions.
