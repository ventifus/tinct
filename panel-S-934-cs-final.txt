#### 1. Pattern matching dispatch completeness

FINDING: Pattern dispatch is COMPLETE and CORRECT | SCOPE: fix-later (informational) | FILE: src/eval.rs:1581-2005 | MODEL: Augustsson (1985), Maranget (2007)

The match_pattern function dispatches on SurfaceExpression variants:
- Placeholder (..) -> wildcard (always matches) [CORRECT]
- VarRef -> pin (look up via de Bruijn, compare with primitive_eq) [CORRECT]
- Int/U64/Float/StringLiteral -> literal equality [CORRECT]
- Field -> constructor tag via flatten_dot_access_to_tag [CORRECT]
- Call (no named_args) -> constructor + positional payload sub-pattern [CORRECT]
- Call (with named_args) -> constructor + named-field sub-patterns [CORRECT]
- Dict -> structural field matching with recursive descent [CORRECT]
- catch-all _ -> Err (reject unsupported forms) [CORRECT]

The catch-all error arm is the right choice: silently returning Ok(None) for unrecognized pattern forms would violate the exhaustiveness contract. The match arms together cover all documented pattern forms from doc/quickstart.md.

Dict pattern handles Value::Overlay (flattening) and Value::Variant (auto-unpacking payload) — these are important for robustness but are not strictly required by the formal model.

No finding to fix.

#### 2. Annotation-based narrowing (T-1761) — TypeScheme.param_narrowings

FINDING: Narrowing extraction is sound but uses stub TypeEnv | SCOPE: fix-later | FILE: src/typecheck_cek.rs:4574,4606 | MODEL: Path-sensitive type narrowing (Siek & Taha 2006 consistency, Garcia et al. 2016 AGT)

The mechanism:
- Pass 4 in typecheck_cek.rs extracts @[narrows: T] from key annotations and @[is: T] from first param annotations
- resolve_annotation is called with a stub TypeEnv::new() (lines 4574, 4606)
- The resolved type is stored in TypeScheme.param_narrowings
- extract_narrowings reads param_narrowings from env via env.read().ok().and_then(|e| e.get_scheme(name))

**Theoretical analysis:**

The approach is sound for simple type names (Int, String, etc.) because resolve_annotation with a stub env resolves built-in type names via TyCon lookup in InferState, which does not require a populated TypeEnv. For user-defined types, the stub env means the resolution will fall through to fresh_type_var (line 4587), which is a safe conservative fallback — the narrowing will produce a fresh variable rather than the intended type, effectively disabling narrowing for that predicate. This is a completeness gap, not a soundness hole.

The `env.read().ok()` pattern in extract_narrowings (line 119) gracefully handles poisoned locks by returning no narrowings — correct behavior under lock failure.

**Race condition assessment:** The Arc<RwLock<Env>> is accessed via read() in extract_narrowings. This is safe because:
- TypeScheme.param_narrowings is written during Pass 4 (insert_scheme)
- extract_narrowings reads during type inference of the function's callers
- Pass 4 completes for a binding before its callers are inferred (SCC ordering)
- The RwLock ensures no concurrent mutation during read

No fix-now finding. The stub TypeEnv is a known limitation documented in the tracker context (C-510: "T-1545 step 4 remains open").

#### 3. ScopeArena free_list reuse correctness

FINDING: Free-list reuse is SOUND — proper reinitialization | SCOPE: fix-later (informational) | FILE: src/arena.rs:57-67,89-99 | MODEL: Pool allocator / region allocator (Tofte & Talpin 1997)

When alloc_root pops from free_list (line 57):
1. scope.parent = None [CORRECT — clears any stale parent pointer]
2. scope.slots was cleared by drop_scope (via clear(), which calls Vec::clear()) [CORRECT]
3. scope.slots.reserve(slot_count) [CORRECT — prepares capacity for new use]
4. Memory budget accounting via record_scope_alloc [CORRECT]

When alloc_child pops from free_list (line 89):
1. scope.parent = Some(parent_id) [CORRECT — sets new parent]
2. Same slot reinitialization as alloc_root [CORRECT]

**Stale ThunkId risk assessment:** After drop_scope clears a scope's slots and pushes it to free_list, any ThunkId with the old scope_id would dereference to None (slot cleared). When the scope is reused, new slots are pushed — but old ThunkIds would index into the new scope's slots at the same positions, potentially returning wrong thunks.

This is mitigated by the Arc<Thunk> indirection: ThunkIds elsewhere in the system hold Arc<Thunk> references directly (via ctx.get_thunk which clones the Arc), so even after the scope is cleared, the original thunk's Arc reference remains alive wherever it was captured. The scope slot clearing only drops the scope's own Arc reference. No use-after-free is possible because Arc prevents premature deallocation.

**Pool allocator invariant:** Every ScopeId in free_list is a valid index into scopes. Maintained correctly.

No finding to fix.

#### 4. drop_range_and_truncate invariant

FINDING: Invariant is CORRECTLY maintained | SCOPE: fix-later (informational) | FILE: src/arena.rs:223-236 | MODEL: Region deallocation (Tofte & Talpin 1997)

The method:
1. Iterates start_env_id..end (line 225)
2. For each scope: counts live thunks, computes scope_bytes, calls record_thunk_free and record_scope_free [CORRECT — accounting matches drop_scope]
3. Calls scope.clear() [CORRECT — frees Arc<Thunk> references]
4. Does NOT push to free_list (line 233 comment) [CORRECT — critical invariant]
5. Calls scopes.truncate(start_env_id as usize) [CORRECT — removes entries]

The comment at line 233 explicitly documents the invariant. The test at line 1493 (test_drop_range_and_truncate_no_free_list_corruption) exercises the exact failure scenario.

As noted in my S-946 review: the latent concern about pre-existing free_list entries with ScopeId.0 >= start_env_id is still present. If drop_scope were ever called on a scope in the truncation range before drop_range_and_truncate, stale entries would remain in free_list. Currently unreachable in production code paths.

No finding to fix.

#### 5. Annotation::Annotated structural change

FINDING: Change is CORRECT and improves expressiveness | SCOPE: fix-later (informational) | FILE: src/ast.rs:200 | MODEL: Higher-kinded annotation syntax

The change from `Annotated(String, Box<Annotation>)` to `Annotated(Box<Annotation>, Box<Annotation>)` enables @[dict]@Inner chaining — the outer position can now be any Annotation variant, not just a string name (Annotation::Simple).

**Semantic meaning of outer vs inner:**
- outer (was String, now Box<Annotation>): the type constructor being applied (e.g., Seq, Map, or a PropertyDict for structural types)
- inner (Box<Annotation>): the type argument being applied to the constructor
- Example: Seq@Int = Annotated(Simple("Seq"), Simple("Int"))

The change is backward-compatible at the Annotation level: all existing code that matched `Annotated(name_string, inner)` now matches `Annotated(Simple(name_string), inner)`. All 14 consumer sites have been updated:

Verified across: ast.rs (get_property, Display), parser.rs (expression_to_annotation, parse_annotation_direct), resolve.rs (walk_surface_annotation), desugar.rs (desugar_surface_annotation), surface_fields.rs (annotation_inner_to_value), surface_convert.rs (dict_to_annotation), typecheck_annot.rs (resolve_fn_return_annotation, resolve_annotation), eval.rs (is_type_node_annotation).

**Serialization round-trip (surface_fields.rs + surface_convert.rs):**
- Serializer: Simple outer emits "name" (backward compat); non-Simple outer emits recursive "outer" field
- Serializer: inner emits both "inner" (flat string, backward compat) and "inner-ann" (recursive, lossless)
- Deserializer: checks "outer" first (structured), falls back to "name" (Simple)
- Deserializer: checks "inner-ann" first (structured), falls back to "inner" (Simple)

This is correct: the two-level fallback ensures old serialized data deserializes correctly while new data round-trips without information loss.

**typecheck_annot.rs resolve_annotation Annotated arm (line 1461-1507):**
- Simple outer: delegates to resolve_type_head (preserves existing behavior)
- Non-Simple outer: resolves outer as Type, produces Type::App(outer_ty, arg)
- Type::App is the correct type-theoretic representation for type application

No finding to fix.

### Axiom Verification

- **Prelude speaks the Rust protocol**: PASS. T-1761 annotation-based narrowing is fully protocol-driven — predicates declare narrowing via @[narrows:T] or @[is:T], Rust reads the declaration from TypeScheme. as_type_dispatch correctly documented as Axiom 1 protocol entry (D-6). No prelude-specific behavior hardcoded in Rust.

- **No fast paths, no fallbacks, no backwards compatibility**: PARTIAL PASS. The hardcoded narrowing arms are deleted (correct). The surface_fields.rs/surface_convert.rs serialization uses "name"/"inner" fallback keys for backward compatibility with old serialized data — this is acceptable as data format migration, not a semantic fallback. One comment says "fast-path" (Finding 8) — nit.

- **Correctness, not performance**: PASS. No performance-driven shortcuts. eval_annotation_property_dict correctly evaluates non-literal annotation values via lower+eval rather than silently dropping them.

- **Loader/prelude agnosticism**: PASS. extract_narrowings reads from env-stored TypeSchemes, not hardcoded function names. Any function with the correct annotation participates in narrowing. as_type_dispatch is declared as a protocol entry. stream.llt correctly uses builtin-parse/resolve/eval pipeline.

- **General case, not specific**: PASS. TypeScheme.param_narrowings is a general Vec<Option<Type>> indexed by parameter position — future extension to multi-parameter narrowing is structurally trivial. The Annotation::Annotated(Box, Box) change is the general form that subsumes the previous (String, Box) special case.
